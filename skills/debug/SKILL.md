# 根因修复纪律

修 bug 的目标是**让错误不再发生**，不是让错误不再被看见。这个 skill 规定怎么挖根因、怎么在根因处动手，以及哪些"看起来修好了"的手法其实是在填垃圾。

## 什么时候读这个 skill

- 修 bug、debug、排错、崩溃、测试失败、接口不通、行为不符预期、性能回退
- 用户说"为什么""怎么回事""定位一下""别打补丁""治本""根因""别糊弄""别绕过"
- 你要改一段你看不懂为什么能跑的代码

## 一、为什么需要纪律

症状是错误的**结果**，不是错误的**原因**。在症状处补一块代码，错误本身还在，只是换了个更难观测的地方出现——而且现在多了一份没人敢删的代码。垃圾代码的利息是复利的：第一处绕过让第二处绕过显得合理，三个月后没人知道哪段是承重墙。

判断一个修复好不好的唯一标准：**同样的根因，换个输入、换个时序、换个环境，还会不会复现**。会，就没修完。

## 二、禁止清单：这些写法是在填垃圾

每一条都写明了"为什么"和"该怎么做"，不是为了禁止而禁止。

1. **吞异常**：`catch (e) {}`、catch 里只 `console.log`、出错返回 `null`。错误是消失了，但它去了哪没人知道。
   → 让错误继续传播；真要处理，就留下可观测的痕迹（状态、事件、明确的返回类型）。
2. **让类型检查闭嘴**：`as any`、`@ts-ignore`、`@ts-expect-error`、`eslint-disable`。类型错误是编译期免费送给你的根因线索，屏蔽它等于把报警器拆了。
   → 搞清楚类型为什么不一致——通常是某处对数据形状的假设错了，那才是根因。
3. **删掉或 skip 失败的测试**：测试失败是最值钱的复现路径，删了它你连验证修复的能力都没有了。
   → 先让测试绿。如果测试本身断言了错误的行为，改它，但要在提交说明里写清楚为什么它错。
4. **用重试、超时、延时藏竞态**：`await sleep(100)`、加 retry 让时序问题不再出现。它没消失，只是概率低了，下次在生产上以更低的概率爆。
   → 找到真正错掉的同步/顺序假设。
5. **特判绕过问题输入**：`if (id === 123) return fallback`。把一条真实数据变成例外，同类数据下次照样炸。
   → 搞清楚这条输入为什么不被支持：校验缺失？契约不清？还是上游发错了数据？
6. **返回默认值让调用方"看起来正常"**：查不到就返回 `[]`、`null`、`0`、`""`。调用方的空指针只是延迟出现了。
   → 区分"真的没有"和"出错了"，用不同的返回值或类型把它表达出来。
7. **硬编码能过当前用例的值**：把动态值写死。测试绿了，真实场景全黑。
   → 问自己：这个值为什么现在算不出来？算不出来的原因往往就是根因。
8. **复制看不懂的代码**：从别处粘一段能跑的。你现在不懂，三个月后也没人懂。
   → 要么读懂再用，要么用更笨但你能逐行解释的写法。
9. **加个 warning 日志然后宣称"已修复"**：日志不是修复，是免责声明。
   → 要么真的修，要么明确告诉用户"这里我只能观测，不能修，因为……"，把边界交还给用户决定。
10. **"重启一下就好了"**：如果重启能修，说明有状态漏到了进程外或时间上——那才是根因。
    → 找那个状态，而不是把重启写进运维手册。

**一句话自检：如果我删掉或改动的每一行都说不出理由，那我就是在堆垃圾。**

## 三、怎么才算找到根因

三条全满足才算，缺一条就继续挖：

1. **能解释所有已知症状。** 包括你觉得"应该没关系"的那个次要现象。解释不了，说明你找到的是另一个症状。
2. **能预测一个还没观测到的现象**，并且你去验证了，预测成立。这是区分根因和巧合的最强证据。
3. **修的是产生错误的机制，不是错误出现的地点。** 如果结论落在历史数据、外部服务、环境配置上，说清楚为什么代码里修不了——那也是诚实的根因结论，但要把边界明确写出来。

## 四、标准流程

1. **复现**：拿到最小、稳定、可重跑的复现步骤。复现不了就先别动代码——去要信息、加观测。把大复现缩成小复现也用二分：把步骤/输入砍一半，仍复现说明砍掉的部分与失败无关，继续砍；不复现就把那半放回来、砍另一半。最小复现是定位的副产品。
2. **定位**：用二分法收敛，禁止跳步猜。把可疑空间每次砍一半，每一步都要有一个可判定的证据（复现/不复现、红/绿、栈变/栈不变）来决定留下哪一半，log₂(n) 步就能把范围压到底。按问题形态选要二分的空间：
   - **怀疑某次改动引入** → 提交二分：`git bisect start`，`bad` 当前提交、`good` 上个正常版本；判定能脚本化就用 `git bisect run ./test.sh`（退出码 0=好、非0=坏、125=跳过），全自动。
   - **怀疑入口到症状点之间的某段代码** → 路径二分：在两端的中点插观测（日志、中间断言、断点），证据指向哪半就留下哪半，再对剩下的一半取中点。
   - **进程卡死、挂起、CPU 100%、不再有新输出** → 栈采样代替猜：进程还活着就连续多次 `pstack <pid>`（或 `gdb -p <pid> -batch -ex "thread apply all bt"`），同一个栈反复出现就是卡点；先 `top -H` 找热点线程、再看它的栈；按固定间隔采样足够多次后做频次统计（poor man's profiler），最高频的栈就是热点路径。JVM 用 jstack，Windows 用 procdump，进程已死改看 core dump。采样是证据不是结论——它告诉你卡在哪，为什么会卡仍回到第 3 步提假设。
   - **测试失败时，先分清"被测代码坏了"和"测试自己坏了"**：报错落在被测系统深处（缺 key、找不到文件、类型不对）时，先和同文件里**能跑的测试**逐项对比配置差异——那个就是现成的正确答案。测试装置撒谎有三种形态：漏传注入点、fake 的 shape 缺字段（缺字段会静默跳过整个被测分支，比字段写错更危险）、断言写法与实现约定不一致（"字段不存在"和"字段值为空"是两件事，用 `not.toHaveProperty` 而不是 `toMatchObject({x: undefined})`）。判据：把被测代码那一行删掉，测试应该红；还绿，说明它根本没测到那行。
3. **假设**：明确写下来——"我认为 X 导致 Y，因为 Z"，并列出两三个可验证的推论。
4. **验证**：用证据证实或推翻。被推翻就回到第 3 步，**不要在原假设上打补丁让它勉强成立**。
5. **修复**：先写一个会失败的测试（就是复现 bug 的那个），再改。改动落在根因处，做最小修改。
6. **复盘**：向用户说清三件事——为什么会发生、为什么以前没发现、同样的模式别处还有没有。

## 五、提交前的自检

- 每一行改动都能说清理由吗？
- 换个输入、时序、环境，这个修复还成立吗？
- 有没有为了让某处"不报错"而写下的代码？
- 留下了 TODO、临时方案、绕过吗？为什么必须留？
- 三个月后的我能看懂这个修复吗？
- 有测试证明 bug 真的没了吗，还是只有我声称它没了？

## 六、这个 skill 自己也要迭代

这个 skill 是写给未来的自己的，不是给现在的我交差的。每次因为根因不清而绕了路：

1. **事后立刻记一条**到 `references/lessons.md`（只追加，不改写历史）：症状 → 根因 → 我当时错在哪 → 下次先做什么。
2. **同一种错犯第二次**，就把对应条目从"建议"升级为流程里的硬步骤（加进第四节或第五节）。
3. **用户说"升级 skill"时**，把 lessons 里反复出现的模式提炼进正文，删掉不再拉得动的规则——skill 会臃肿，臃肿的 skill 会被无视。
4. **每次改完 skill 都要告诉用户改了什么、为什么**，不让 skill 在用户不知情的情况下变形。

- `references/lessons.md`：累积的真实教训。每次排查前先扫一眼，能省一次重复犯错。
