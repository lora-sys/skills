# 教训记录（append-only）

格式：**症状 → 根因 → 我当时错在哪 → 下次先做什么**。

只追加，不改写历史。把某条提炼进 SKILL.md 正文时，在原文末尾加一行 `→ 已进正文第 X 节`，别删原文。

## L1 报错文案把"我没读到"说成了"你没声明"

- **症状**：`agent:up` 抛 `Target checkout does not declare a readable database version`。
- **根因**：启动器用正则 `/if\s*\(\s*version\s*>\s*(\d+)/` 从源码里抠版本号，而源码早已改成导出常量 `CURRENT_SCHEMA_VERSION`，正则匹配不上。代码把"我没匹配到"写成了"你没声明"。
- **我当时错在哪**：把报错文案当成事实，准备去改被冤枉的目标仓库；没有回头读产生这条报错的那几行，确认它说的和它做的是否一致。
- **下次先做什么**：报错文案是代码写的，也会骗人。先读产生这条报错的代码，比对"它声称的"和"它实际做的"。

## L2 检查工具自己坏了，报出"全都坏了"

- **症状**：脚本报告 14 个分支里有 6 个缺少 skill 文件。
- **根因**：`git cat-file -e "$B:.agents/..."` 在 Git Bash 里被 MSYS 路径转换吃掉了冒号，命令本身失败，失败被误读成"文件不存在"。
- **我当时错在哪**：相信了一个我没验证过的检查命令；对"大部分都坏了"这种戏剧性结论没有提高警惕。
- **下次先做什么**：结论越严重越要复验。换第二种方式（`git ls-tree`）交叉验证，再下结论。先怀疑检查本身，再怀疑被检查的东西。

## L3 看不见 ≠ 不存在

- **症状**：skill 已经成功提交到 main，`/` 菜单里却看不到。
- **根因**：skill 发现是从会话 cwd 逐级往上扫 `.agents/skills`，且从不进入子目录。会话根在 `repos/`，skill 在 `repos/Glassbox-Agent-Harness/` 里，差一级——扫描范围根本覆盖不到。
- **我当时错在哪**：默认"提交了 = 到处都是"，没去确认发现机制的范围就下了"skill 坏了"的判断。
- **下次先做什么**：东西找不到时，先问"它按什么规则被找到"，再问"它在哪"。规则和位置对不上，那就是根因。

## L4 规则写得很凶，但能力不存在 = 必然被违反

- **症状**：某 skill 白纸黑字写着"trace 操作永远走本 skill 附带的 CLI，不要临时写解析脚本"，实际执行的 agent 却现写了一个临时 `gbx-inspect.mjs` 去读库表结构。
- **根因**：那个 CLI 根本没有查数据库的命令。规则要求一条不存在的能力，agent 在时间压力下只能自己造一个——**违反纪律的根因是能力缺口，不是态度问题**。
- **我当时错在哪**：把"写了禁止临时脚本"当成 agent 偷懒，第一反应是把规则写得更凶（"严禁""绝不允许"）。方向错了：规则加粗只会让下一个人更隐蔽地违反，不会让他有工具可用。
- **下次先做什么**：发现有人违反 skill 里某条规则时，先问"这条规则要的能力，skill 给了吗？"。没给，就去补能力（加命令、加脚本、加文档配方），而不是加粗措辞。补完要用真实的输入跑一遍——同上，我第一版配方就因为环境变量传不进而失败。

## L5 测试失败的根因经常在测试自己身上，被报错信息指去了别处

- **症状**：新写的 adapter 测试报 `status: "error"`，`text: ""`，断言全空。第一反应是"被测代码有 bug"。
- **根因**：那条报错信息指向**被测系统缺 API key**，而真实根因是我的测试少传了一个 `createSession` 注入点——同文件里 3 个能跑的测试全都注入了它。缺了它，被测代码才真的去建真实会话，才真的去要 key。**报错说的是"下游坏了"，但下游之所以被访问，是我的测试漏了一个上游配置。**
- **我当时错在哪**：按报错信息去改 scope（group → private）——这是典型的"为了消症状而改"，改完照样失败，白绕一圈。没有先和同文件里**能跑的测试**逐项对比配置差异。
- **下次先做什么**：测试失败且报错在被测系统深处时，先做一次"和通过的同类测试的差异对比"——构造参数、mock/fixture 注入、请求作用域，一项一项对。能跑的那个是现成的正确答案。改 scope、改数据、加兜底之前，先确认测试自己的装置是完整的。

→ 已进正文第四节（定位第 2 步）。

## L6 用 `toMatchObject` 断言 `undefined` 会失败，因为实现有意不写入那个键

- **症状**：`expect(events[0]).toMatchObject({ threadId: undefined })` 失败，实际值里没有 `threadId` 这个键。
- **根因**：实现遵循"没有的字段就不写"，而 `toMatchObject` 要求键存在。是我的断言写法和实现的"可选字段缺省即省略"约定不一致——不是实现的 bug。
- **我当时错在哪**：先怀疑实现漏了字段，准备去"补上 threadId: undefined"——那恰恰是在往证据里塞噪声字段，反向破坏设计。
- **下次先做什么**：断言一个字段"应该不在"时，用 `not.toHaveProperty("x")`；断言"应该在"时才用 `toMatchObject`。先分清"字段缺失"和"字段值为空"是两件不同的事，再去判断哪个才是对的。

→ 已进正文第四节（定位第 2 步）。

## L8 测试通过不代表测试工件已清理

- **症状**：Statechart 全量测试本身通过，但多轮运行后 `/tmp` 留下了 1,896 个 `statechart-*` 临时目录。
- **根因**：多个测试文件直接调用 `mkdtempSync`，只清理了部分子路径；测试进程结束时没有统一清理其余目录。
- **我当时错在哪**：只看测试退出码，没有在测试结束后检查临时目录；导致本地工作痕迹持续累积。
- **下次先做什么**：测试创建临时目录时使用每个测试文件独立的 factory 登记，并在文件结束钩子中清理全部目录。逐项尝试删除，最后汇总清理错误；验证结束后对照运行前后的目录计数。测试自身需要保留的工件仍由测试明确管理。

## L7 fake 的 event shape 撒谎，会让一段本该被测的逻辑整段跳过

- **症状**：给 `turn_end` 加 `stopReason` 后断言拿不到值；第一次排查以为是改动没生效。
- **根因**：测试里的 fake session 发的是 `{ type: "turn_end", message: {} }`——`message.role` 不是 `"assistant"`，于是被测代码里整个 `role === "assistant"` 分支被跳过，我要测的字段根本没被走到。**fake 缺字段比 fake 字段错更危险：错的会报错，缺的会静默跳过。**
- **我当时错在哪**：相信了 fake 是"够用的"，没有核对被测代码在哪个条件下才读我关心的字段。
- **下次先做什么**：给被测字段写断言前，先在 fake 里造出能走到那段代码的最小真实 shape。判断标准：如果我把被测代码的那行删掉，测试应该红——删了还绿，说明测试没测到它。

→ 已进正文第四节（定位第 2 步）。

## L9 原子替换后的 chmod 仍留下可见性竞态

- **症状**：channel 的 `done.json` 最终权限可读，但控制器偶发在文件刚出现时收到 `PermissionError`。
- **根因**：写入端先 rename 发布默认 0600 的临时文件，再由 `share_output()` chmod；轮询读取者能在这两个操作之间看到不可读文件。
- **我当时错在哪**：只检查了最终权限和正常路径，没有把原子发布点当作消费者可见的瞬间。
- **下次先做什么**：共享文件的目标 mode 必须设置在临时 inode 上、rename 之前；用 `Path.replace` 的确定性回调断言发布瞬间的权限，不靠延时或重复读取掩盖竞态。

## L10 完成标记的父目录也必须先可访问

- **症状**：把 `done.json` 的 mode 提前设为 0644 后，仍不能排除读取者在目录权限更新前撞上 `PermissionError`。
- **根因**：发布完成标记前，响应目录本身也需要执行/读取权限；文件可读但父目录仍为 0700，路径依然打不开。
- **我当时错在哪**：第一版回归只在 rename 前检查临时文件 mode，没有模拟严格 umask 下的新响应目录。
- **下次先做什么**：先共享响应目录和已有产物，再以目标 mode 原子发布完成标记；在 umask 077 下同时断言父目录与临时文件在 rename 前可访问。

## L11 外层解析成功不代表隔离运行时拿到原 provider key

- **症状**：CLI 能解析 StepFun provider，Docker secret resolver 的单独检查也能取到合成值，但 Native SDK 实际启动时仍报 `STEPFUN_API_KEY` 缺失。
- **根因**：SDK 先启动隔离控制容器，再由控制容器启动 Agent runtime。外层解析把凭据映射成 `ABB_AGENT_MODEL_*`，而内层 runtime 按 provider 配置再次查找原始 `credential_env`。该变量名没有进入 staged manifest 的 `runtime.worker_env_keys`，因此没跨过容器边界。
- **我当时错在哪**：把宿主侧 resolver 检查当成完整验证，没有检查 staged manifest 和最终传入容器的环境变量。
- **下次先做什么**：逐个检查进程和容器边界；用合成凭据断言 provider 的 `credential_env` 名称进入 `worker_env_keys`、运行时确实收到值，并确认值不进入 manifest 或证据文件。

## L12 控制器和 Agent 共用 manifest 不代表应共用全部密钥

- **症状**：Native SDK 的 Agent runtime 正确取得 MCP 环境变量，但同一评测流程启动的 SDK 控制器容器也继承了这些值。
- **根因**：`run_evaluation` 用同一份已暂存的 `agent.toml` 分别启动控制器和 Agent；Docker runtime 默认把 manifest 声明的环境变量传给两个容器，而 MCP 的 `env_keys` 只应进入 Agent 的 ACP 子进程。
- **我当时错在哪**：验证了 Agent 能读取 MCP 值和证据脱敏，却没有审计同一 manifest 的其他容器消费者。
- **下次先做什么**：对每个由同一 manifest 启动的容器分别列出必需环境变量；在启动参数层验证控制器排除 Agent 专用密钥，并验证 Agent 仍收到所需值。
