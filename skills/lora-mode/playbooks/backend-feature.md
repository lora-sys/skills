# backend-feature: 后端服务、API、脚本与工具

> **适用**：后端服务、API、CLI 脚本、数据处理工具、爬虫类开发。**主导 skill**：无专门 skill，按本 playbook 执行并遵循 `debug` 纪律。

## 步骤

1. **识别现状。** 运行方式（本地/部署）、语言与依赖管理、现有入口、配置与凭据来源、输出消费方。
2. **核实技术事实。** 库与运行时版本查官方文档；CLI 参数用 `--help` 验证，不凭记忆。
3. **出计划。** 方案回答六问：功能完成后用户能看到什么变化、采用什么实现方法、预计修改哪些模块、异常情况和技术风险是什么、哪些决定需要用户做、如何测试和验收。说明要可执行，不能只复述需求或堆砌细节。列出接口契约或 CLI 约定（输入/输出/退出码）、数据模型、错误路径、日志和依赖变更。按任务与真实源码轻量筛查并发/顺序、幂等、数据不变量与一致性、资源边界和权限隔离；存在具体性质或已有验证覆盖时读 `../references/verification-routing.md`，没有时不增加额外验证机制。通用问题先路由到同目录 `investigation.md` 找成熟方案（拿到结论后回到本 playbook 继续），不重复造轮子。
4. **实现。** 数据形状先行；外部输入一律验证结构与边界；显式错误处理，不吞异常；机密只从环境读取。
5. **分阶段验收（强制）。** 修改模块时运行相关静态检查和单元测试；功能完成后运行模块集成测试；合并前及发布前运行完整端到端测试。另真实运行主路径和相关失败/边界路径；按筛查结果选择足够的属性测试、fuzz、仿真、运行时检查、模型评测或形式化验证，命中已有正式验证覆盖时维护并复跑。仅在有性能要求或性能退化时分析代码链路并用火焰图定位优化点。复杂或重复测试链路封装成 CLI/脚本。新工具类任务给一条可复制的运行命令并记录实际输出。避免每次小修改都运行完整套件。
6. **按规模审查。** 审查业务正确性、完整流程、复杂/冗余/难维护实现、测试有效性，以及基础设施、组件、函数和框架的复用。分别验证代码、测试结果和真实用户交互；单元测试通过不代表功能完成。M 档行内点查输入边界、错误路径、状态诚实和回归面；L 档按 `../references/review-protocol.md` 做隔离审查。若改动随后进入 PR，由 `pr-open` 的一次独立审查替代本步骤。
7. **按证据交付。** 运行输出、测试结果、日志片段；说明适用范围与未做路径。

## 证据形态

真实命令与输出（成功+失败路径）、测试结果、错误路径演示。

## 移交

需要 Web 界面配套 → `web-feature.md`；需要上线 → 与用户确认部署方式后走对应发布流程（本 playbook 不含部署）。
