# code-cleanup: 代码库清理与 AI slop 审计

> **适用**：用户明确要求清理 AI slop、死代码、无用抽象、过期文档或注释。功能 PR 的局部清理走 `pr-open.md`，不执行本 playbook 的全仓审计。

## 判定范围

- 用户指定文件或功能时，仅审查指定范围及其直接调用方。
- 用户要求整理整个代码库时，先执行全仓审计并输出候选清单，仅处理已获授权的低风险项。
- 按风险与影响面定级（S/M/L）。重点核查动态加载、公开接口及持久数据影响，不以改动行数为主导。
- 清理后必须保持既有对外行为与系统不变量，不得以缩减代码行数为目标。
- **S：** 仅清理少量指定文件，检查目标差异、直接调用方和相关测试；跳过全仓盘点。
- **M：** 涉及多个关联模块时，检查相关入口、配置、CI、测试和直接消费者；运行覆盖这些模块的现有门禁。
- **L：** 用户要求全仓清理，或候选影响公开接口、动态加载、依赖、CI、持久数据或多个系统边界时，执行下方完整审计，并运行适用的 lint、类型检查、测试和构建基线。

## 全仓审计（L 档或明确要求全仓）

1. **确认起点。** 检查仓库结构、工作区状态、默认分支、构建配置、测试命令、CI、应用入口和架构规则。保护未提交的用户改动；代码修改必须使用独立任务分支。记录 base 与 head SHA，避免将既有改动计入本次清理。
2. **记录基线。** 从既有配置中识别 lint、类型检查、测试和构建命令。运行适用的仓库门禁，逐项记录执行命令、实际输出与既有失败项。未经用户明确授权，不得为分析工具安装新依赖。
3. **收集候选。** 优先使用项目已有的死代码分析、依赖检查或代码复杂度工具。缺乏现成工具时，结合语言服务器、编译器报错、测试覆盖与全局搜索。静态分析结果仅作为候选，不单独构成删除证据。
4. **核实可达性。** 检索跨模块调用、字符串引用、动态导入、文件系统路由、插件注册表、脚本入口、公开 API、代码生成和运行时配置。完整追踪候选代码的调用方与消费方。
5. **检查设计与错误路径。** 审查重复辅助函数、纯转发包装、过度抽象、无效防御分支、静默吞错和冗余实现。保留记录业务原因、安全边界或隐式不变量的关键代码。
6. **审计文档与注释。** 对照当前代码、配置及 CI 核实 README、AGENTS.md、docs 及其他 Markdown 文件。将文档明确标注为有效、过时、已替代或历史归档。删除复述代码逻辑的注释、已注释代码块和过期调试输出；保留业务背景、约束、许可证与工具指令。注释清理遵循 `references/comment-review.md`；文档改写遵循 `engineering-writing` 与 `unslop`。
7. **先列清单。** 逐项记录文件路径、代码位置、拟删除内容、删除理由、引用证据、风险等级和验证方式。单独标出涉及动态加载、公开 API、数据库迁移、生成代码、运行配置或兼容路径的边界项。仅自动处理高置信度、低风险的代码行、注释或局部实现。
8. **分批修改与复验。** 每批次仅处理一类核心问题。每批修改后立即运行覆盖受影响行为的检查，并与基线严格比对。新增失败必须先定位修复；既有失败如实保留记录。检查 diff，确保不引入无关重构或格式化噪声。
9. **汇总证据。** 完整报告已删除的文件、代码行、依赖、文档和注释；附带 lint、类型检查、测试和构建结果；列出未解决风险。可提出针对本次发现的 CI 规则建议，但未经授权不得擅自新增 CI 配置。

## 删除边界

- 不得仅凭未引用报告直接删除文件、依赖、插件、公开接口、数据库迁移、兼容路径或动态加载模块。
- 删除版本受控文件或分支前，必须先提供精确清单、关联证据与风险说明，暂停等待用户显式确认。用户笼统要求「清理」不构成删除授权。
- 证据不足的候选仅列入待确认清单。不得使用大范围 ignore 规则掩盖分析结果，亦不得在缺乏针对性验证时声称行为不变。
