# eval: 验证技能行为变化

**适用**：用户要求评估技能，或技能改动会改变可观察的路由、权限或交付行为。纯措辞调整、普通代码改动和一次性任务不走本流程。

## 流程

1. **写清目标。** 指明被测的旧/新版本和一个真实任务场景。准备 3–6 条可观察的判据，只给评审者看。
2. **准备隔离环境。** 每个版本使用独立工作副本和干净会话，放入该任务自然需要的项目材料。不要让被测 Agent 看到 case 编号、评分标准、另一版本或"正在评测"等提示。
3. **写自然任务。** 用用户会实际提出的请求。相同版本对比必须使用同一 prompt 和等价环境；不要提示 Agent 报告自己加载了哪些技能。
4. **运行对照。** 对旧、新版本分别运行。优先保持模型和工具相同，避免把模型差异当作技能收益。若工具支持，匿名化输出后让独立评审者按同一标准比较；不支持时按判据逐项核对产物与实际执行记录，并标明评审未盲。
5. **核对行为证据。** 检查实际加载的文件、执行的命令、产物和环境状态。Agent 自述不算证据。只按本次判据评分，不添加事后标准。
6. **作出结论。** 新版本满足目标且旧版本未满足，才算该场景显示改进。两版都通过说明没有测出差异；两版都失败说明标准、场景或实现需要重看。不能把单个场景的结果外推成整体质量。
7. **维护案例。** 只保留能区分行为或覆盖已确认回归的 case。记录 prompt、隐藏判据、版本、证据和限制；删除重复或无法判定的 case。常规任务只运行直接相关的 case，不加载或运行完整 suite。

路由和权限变化至少覆盖一条允许路径与一条禁止路径。完整 suite 仅在用户要求或正式发布前运行。

本流程参考 [pstack eval playbook](https://github.com/backnotprop/pstack/blob/main/skills/poteto-mode/playbooks/eval.md)，并按本仓库工具与委派规则简化。
