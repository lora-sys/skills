# goal-eval — 目标驱动的质量迭代

**适用**：用户要把模糊质量目标变成 Eval，并迭代到目标分数、指标或对照结果。普通 bug 修复和按明确规格交付走原流程。

1. **定目标。** 从目标提炼 3–5 个可观察断言，至少一个不得退步的条件。沿用用户给出的门槛；没有门槛时，按当前差距定一个可达目标并标为推定，只有涉及产品取舍时才询问。优先用二元断言；需要评分时复用已有锚点，否则固定 1–5 锚点。
2. **跑基线。** 对当前产物运行这些断言，保存真实结果、截图或测量值。无法测量的维度标为未知；不要编造分数或 token 数。
3. **单点迭代。** 每轮只改一个假设，再跑受影响的断言和全部不回归条件。只接受评分提升且无已通过项回退的版本。比较主观质量时复用同一锚点；主观评分用独立盲评者，只给产物与固定标准；无盲评能力时标为未独立验证，不自评达标。Agent 或工具行为用相同 prompts 在干净会话中比较基线与候选，受测 Agent 不接收评分答案。
4. **保留最佳。** 记录本轮候选与最佳版本差异。回退只撤销本轮候选改动，不覆盖用户已有工作，不用 `git reset --hard`。
5. **停止并交付。** 达到目标、连续两轮无提升、最多三轮、预算到限或需要用户作产品决策时停止，交付当前最佳版本、逐项分数及证据。若目标含压缩，先通过正确性 Eval 再做一次精简，并复跑全部断言。

界面目标按需使用 `oil-ui` 的视觉评审锚点，代码实现交给 `web-feature` 或 `visual-refinement`；工具描述和 Agent 行为用真实场景断言。只有确认可复用的失败才加入长期 `EVALS.md`。按目标连续执行，不逐轮请求确认；外部写入、公开发布等仍遵守各自授权门。
