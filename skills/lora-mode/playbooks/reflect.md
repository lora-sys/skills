# reflect: 复盘与自我迭代

> 本 playbook 是 lora-mode 自我迭代的唯一入口。
> **适用**：用户要求复盘，或同一类路由、权限、质量问题再次出现。单次任务、一次性偏好或已由现有检查拦住的问题不自动触发。**主导 skill**：skill-creator（产新 skill 时）、github-gem-seeker（先找轮子）。

## 数据源（没有证据不立项）

1. 本次会话中可复现的失败、重复纠正或浪费步骤。
2. 相关的 `evals/EVALS.md` case、代码证据和现有规则。
3. debug 的 `references/lessons.md`，仅当问题属于调试纪律时读取。

## 步骤

1. **汇集证据。** 只分析重复或可复现的问题。写明触发条件、实际行为、预期行为和现有规则为何没有阻止它；没有具体证据就停止。
2. **三类出口分流。**
   - **小修**（措辞、步骤增删、阈值调整，单处 ≤5 行）：直接改对应 playbook/references。一次复盘最多 3 处。
   - **结构性改动**（新增/合并 playbook、改分级规则、改硬边界）：只出方案与证据，用户拍板后再动。
   - **新 skill**（同类问题第三次出现，或 github-gem-seeker 找到值得固化的方案）：交给 `skill-authoring.md` 和 skill-creator。先在本仓库写草案并运行测试 prompt，再由用户决定是否提交；不跳过测试直接安装。
3. **修到能执行的层级。** 优先消除架构中的错误入口；否则依次用类型、lint/CI、测试拦截。只有依赖判断的规则才写进 skill。每条新规则都要能关联到这次证据。
4. **复测（强制）。** 只跑受影响的 case。路由或权限改动用干净会话测允许与禁止路径；同一 case 要能区分旧规则和新规则。完整 suite 只在用户要求或正式发布前运行。未运行的检查标为未测。
5. **按证据交付。** 说明问题证据、选择的修复层级、修改内容和复测结果；结构性改动或新 skill 等用户决定后再做。

## 纪律

- 不把一次性偏好写成通用规则。
- 同一指引重复失效时，优先加可执行检查，文档规则放最后。
- 新 skill 与结构性改动必须用户拍板；小修可自治但全部留痕、可回滚（git）。
- 复盘本身是 M 档任务；改后复测才允许交付。
