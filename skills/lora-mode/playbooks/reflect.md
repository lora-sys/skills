# reflect: 复盘与自我迭代（循环 B）

> 本 playbook 是 lora-mode 自我迭代与工程体系改进（循环 B）的唯一入口。
> **适用**：用户要求复盘，或同类系统性路由、权限、架构边界与质量问题再次出现。
> **主导 skill**：skill-creator（产新 skill 时）、github-gem-seeker（先找轮子）。详见 `references/codebase-governance.md`。

## 双循环模型与启动门槛

研发系统由「环 A（功能交付）」与「循环 B（工程改进）」构成：
- **环 A（功能交付）**：明确需求 → 局部实现 → 分层验证 → 修复失败 → 提交证据。负责日常业务进度与完成率。
- **循环 B（工程体系改进）**：发现错误 → 确认根因与边界 → 改进约束规则 → 增加自动检查 → 补充回归用例 → 自动继承新约束。负责使后续任务更安全、更易执行。

### 启动门槛（严防过度设计）
1. **执行时序**：必须在当前任务的「环 A」交付完成后启动，绝不打断正常业务功能交付。
2. **拒绝偶发小错**：绝不为每个偶发、个别或轻微错误增加永久规则；避免陷入无休止的重构与规范膨胀。
3. **准入条件**：只有当错误代表**通用系统性风险**（如跨模块循环依赖、私自绕过公共接口、核心不变量失效）、**修复代价极高**，或**同类问题重复出现（≥2 次）**时，才进入本 playbook 固化工程约束。

## 循环 B：六步闭环流程

1. **发现错误与受损不变量。** 识别系统在开发或运行中出现的具体问题（如循环依赖、越权访问、状态机非法跳跃）。记录触发条件、受损文件与实际行为。
2. **确认根因与边界模糊点。** 深入分析是模块职责划分不清、公开契约不严谨，还是公共能力未下沉。没有具体可复现证据就停止。
3. **改进约束规则（三类分流）。**
   - **硬规则**：涉及权限、接口类型、模块边界、禁止依赖时，定义确定性的允许/禁止规则，配置工具自动化拦截。
   - **过程规则**：涉及验证时序、交付证据、CI 门禁时，更新流程规范并增加自动化检查脚本。
   - **判断规则**：涉及重大架构权衡、非功能指标时，记录架构决策记录 (ADR) 并提交评审。
4. **增加自动检查机制。** 将新规则转化为程序化拦截（静态依赖检查如 dependency-cruiser、ESLint 规则、架构测试或预提交钩子），严禁仅停留在口头说明。
5. **添加回归用例。** 编写专门的破坏性测试用例或负向用例，确保违反新约束的代码在构建或测试时被确定性拒绝。
6. **下一次开发自动使用新约束。** 验证新检查在干净环境生效，后续 Agent 进入项目时自动受新规则与工具保护，杜绝同类错误复发。

## 三类交付出口

- **小修**（规则微调、步骤增删、阈值调整，单处 ≤5 行）：直接改对应 playbook/references。一次复盘最多 3 处。
- **结构性改动**（新增/合并 playbook、改分级规则、改硬边界、调整架构依赖）：只出方案与证据，用户确认后再动。
- **新 skill**（同类复杂测试或开发流程第三次出现，或 github-gem-seeker 找到值得固化的成熟方案）：交给 `skill-authoring.md` 和 skill-creator。先在本仓库写草案并运行测试 prompt，再由用户决定是否提交；不跳过测试直接安装。

## 纪律

- 不把一次性偏好写成通用规则。
- 同一指引重复失效时，必须增加可执行检查（硬规则），文档规则放最后。
- 循环 B 改动必须附带测试证据并保持可回滚。
