# web-feature: 前端 / 全栈 Web 功能与页面

> **适用**：新建或改造 Web 应用、页面、组件、交互。**主导 skill**：oil-frontend（实现）、oil-ui（设计判断）。代码库治理标准见 `references/codebase-governance.md`。

## 步骤

1. **识别现状。** 读仓库约定、package.json/锁文件、脚本、现有组件、部署配置；判定新建 vs 改造。改造项目保留既有架构与工具，不为新而迁移。
2. **核实技术事实。** 新建项目、升级依赖或用不熟悉 API 前，查官方文档与当前稳定版本；不凭记忆写版本、命令或 API。
3. **出计划（环 A 交付）。** 方案回答六问：功能完成后用户能看到什么变化、采用什么实现方法、预计修改哪些模块、异常情况和技术风险是什么、哪些决定需要用户做、如何测试和验收。说明要可执行，不能只复述需求，也不能堆砌技术细节。列出目标与非目标 (Non-goals)、核心对象、状态机与不变量、用户流/信息架构、组件公开契约、数据/API 契约、依赖变更和部署状态。遵循单向依赖，禁止循环引用。选型读 `references/web/stack-selection.md`。
4. **设计判断（按需）。** 涉及新界面、视觉方向或多风格选择时，先调度 oil-ui 出对比页，用户选定后再动工；纯逻辑改动或小改动可跳过，但须在 todo 记录原因。视觉/动效标准读 `references/web/design-motion.md`。
5. **实现最小正确变更。** 调度 oil-frontend；数据形状先行（先写状态与数据结构，再写界面）；按项目结构与命名实施；改动收敛在模块内部；发现相邻问题记录不顺手修。
6. **分阶段验收（强制）。** 按 7 级分层验证矩阵（数据/业务/权限/集成/操作与视觉/异常/回归）逐步执行。把测试拆成独立模块。修改模块时运行相关静态检查和单元测试；功能完成后运行模块集成测试；合并前及发布前运行完整端到端测试。交互、视觉或产品流程变化时做人工体验验证；性能要求或退化时用火焰图定位优化点。重复浏览器操作和复杂测试链路封装为 CLI 或脚本。保留验证核心业务约束的简单测试。按改动安排测试时机，避免每次小修改都跑完整套件。具体门禁读 `references/web/quality-gates.md`。
7. **按规模审查。** 审查业务正确性、完整用户流程、复杂/冗余/难维护实现、测试是否有效或重复，以及基础设施和现有组件是否可复用。分别验证代码、测试结果和真实用户交互；单元测试通过不代表功能完成。M 档行内点查输入边界、错误路径、状态诚实和回归面；L 档按 `../references/review-protocol.md` 做隔离审查。若改动随后进入 PR，由 `pr-open` 的一次独立审查替代本步骤，避免重复。
8. **按证据交付。** UI 变更附前后截图，动效附录屏，并报告实际验证结果和未完成项。项目 `AGENTS.md` 要求上传证据时，用 `file-upload` 传这些媒体（默认 `temp`），把返回的链接交给 `file-pr` 写进 PR 正文；上传受阻时如实标注，不隐瞒失败。若改动涉及系统性边界模糊，交付后进入 `reflect.md` 执行循环 B。

## 证据形态

构建/测试真实输出、浏览器前后截图（窄+宽）、录屏（动效/多步交互）、审查核验记录。

## 移交

验证媒体需要公开链接 → `file-upload`；链接要写进 PR → `file-pr.md`；需要公开链接或上线 → `publish.md`；存量站整体改造 → `static-site-release.md`。
