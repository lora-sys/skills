# 项目 AGENTS.md 规范与模板

项目 `AGENTS.md` 是常驻上下文。流程由 lora-mode 与项目内 skill 承担；本文件只记录本仓库特有、难以从代码推断且违反代价高的事实。项目文件中的明确禁令优先于 skill 的默认流程。

## 写入判据

按顺序判断，命中即停：

1. 能机械执行 → 放进 lint 或 CI；正文只留规则名或命令指针。
2. 读代码、`package.json` 或配置能得出 → 不重复写。
3. 与具体仓库无关的通用偏好 → 放全局 `AGENTS.md`。
4. 超过 5 步的流程 → 放 `.agents/skills/<name>/SKILL.md`；正文只留指针。
5. 只有本仓库成立，且违反代价高 → 写入项目 `AGENTS.md`。

预算：单仓库不超过 150 行。每条约束写成可检查的事实。命令必须能从干净 checkout 复现，并写明工作目录。陷阱要说明后果和正确做法。不写密钥、内网地址或个人链接。代码库治理完整标准见 `references/codebase-governance.md`。

## Agent workflow

日常开发遵循「环 A（功能交付）」：明确需求 → 局部实现 → 运行验证 → 修复 → 提交证据。
若遇到系统性错误、高代价违规或同类问题复现，交付后触发「循环 B（工程改进）」沉淀自动检查与回归用例。

- 改动范围：需求变动尽量收敛于模块内部，不影响无关模块。
- 临时材料：不要把临时计划或 Agent 草稿提交进仓库。长期决策写入对应文档或 Issue。
- 交付差异：<只写覆盖通用提交、PR 或报告流程的项目规则>

## 反面清单

- PR 创建规则、禁止直推默认分支、变更影响图、证据对应最新 head、S/M/L 分级：lora-mode 已有。项目文件只写覆盖默认行为的差异。
- 「任何改动都要加测试」：与 lora-mode 的任务分级冲突。写清哪些行为需要验证，以及适用的检查。
- 完整 runbook：放 `docs/operations/`，正文留链接。
- 历史沿革与决策过程：放 `decisions/` (ADR) 或 PR 描述。
- 逐文件目录说明、字段清单和实现复述：代码已记录，正文不重复。
- Evals 不替代测试；不要把普通逻辑正确性列为模型评估目标。
- `AGENTS.md` 不重复完整架构、开发 runbook 或用户手册；它说明边界并把 Agent 路由到相应文档。
- 不要把临时计划、Agent 草稿或研究笔记作为项目文档提交。
