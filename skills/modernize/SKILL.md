# Modernize

先判断 PR 的目标是否仍成立，再决定是否更新分支。无冲突不代表实现仍适用。

## 核实目标和现状

1. 记录 PR URL、状态、base、head 仓库与分支、作者、最新 SHA、检查和 review。读取标题、正文、关联 Issue、评论、提交和完整 diff。
2. 更新目标 base、PR head 和相关分支的本地引用，记录 merge-base。检查 PR 分叉后 base 上的提交，以及相关的已合并和开放 PR。
3. 对照当前代码、API、类型、schema、依赖和架构，确认原问题是否仍存在，是否已有更好的实现，以及原实现是否会恢复旧行为或重复拥有同一职责。
4. 把观察到的事实与判断分开记录。不能只根据 PR 年龄、无冲突或已有投入判断它应继续。

## 选择处置方式

- **MODERNIZE**：目标仍有价值，现有实现仍符合当前架构。更新分支并完成对应检查。
- **REWORK**：目标仍有价值，但现有实现已不合适。说明需要重做的最小范围；在用户要求完成这项重做或 full-send 前，不推送新的实现。
- **CLOSE**：目标已解决、被取代或不再值得维护。给出具体证据；本技能不授权关闭 PR。

## 更新分支

- 当前工作区有用户改动时，使用隔离 worktree。
- 他人拥有的源分支保持只读。需要修改时，在任务自己的分支上重做必要变更，并按 lora-mode 的 PR 流程创建 replacement PR；保留可核实的提交作者和署名。
- 只对本任务拥有的分支执行 rebase。rebase 前记录远端 head SHA；推送改写后的历史时用 `--force-with-lease` 锁定该 SHA。不要改写贡献者分支或共享历史。
- rebase 后用 `git range-diff` 对比原提交系列，并检查最终 diff，确认原有意图仍在且没有重新引入已落地主干的行为。
- 运行受影响区域的检查，区分代码失败、预存失败和基础设施故障。

PR 创建、跟进、full-stop/full-send、评论、合并和合并后清理都按 lora-mode 对应流程及其授权边界执行。本技能本身不授权远端写入。

## 汇报

先给出 `MODERNIZE`、`REWORK` 或 `CLOSE` 及理由，再列出主干变化、实现是否仍适用、完成的更新、实际检查和未验证事项。需要用户决定的事只在确实改变结果时提出。
