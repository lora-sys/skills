# Review loop

用一位独立审查者检查当前任务的代码差异。主 Agent 负责判断发现、修改和验证。审查者只读，不提交、不推送、不评论 PR，也不启动其他 Agent。

## 预算与模型

- 默认最多 3 轮。第一轮审查完整范围；后续轮次只看新改动和未解决发现，不重开已解决的部分。
- 只有安全、权限、认证、数据丢失、状态/并发风险仍有证据支持的 blocker / should，或用户明确要求时，才可延长到最多 5 轮。达到预算不等于通过。
- 如果一轮只剩 nit，提前停止。纯评论、文档或格式改动不触发新一轮。
- 一次循环固定一位审查者和一个模型；后续轮次沿用同一模型，串行复审。不启动 council、并行审查者或嵌套审查。
- 在 T3 Code 中先读当前 `orchestrator_capabilities`。排除 GPT-6.1-Sol。优先选择能力列表明确标为 free 的独立审查模型；否则只用用户或项目指令明确授权的低成本模型。不要凭 `flash`、`small` 等名字推断价格。没有已授权的低成本模型时，停止在委派之前，说明缺少什么，不得静默改用付费模型。
- 能选时，审查者应与主 Agent 来自不同模型系列或 provider。不要为提高覆盖面启动 council 或多名并行审查者。
- 只记录工具实际给出的 provider、model、effort、usage 或费用；没有返回的数据写“未提供”，不估算。

## 界定审查范围

1. 读取用户意图、仓库状态和适用检查。确定 base、head、改动路径及不在范围内的内容。PR 用远端 base 与当前 head；本地改动用用户指定 base 或默认分支。不要凭空选择比较基点。
2. 不 stash、丢弃或纳入无关更改。若能按任务路径隔离，就只审查这些路径；若无法把当前任务与其他未提交更改区分开，先说明阻塞。
3. 使用同一份 base-to-working-tree diff 贯穿所有轮次，包含相关未跟踪文件。记录已运行的检查、失败项和未运行项，避免把预存失败归因于当前改动。

## 发起审查

第一轮给审查者一份无父级历史的简短任务书，包含 repo、base、head、意图、范围边界、检查结果和读取 diff 的方法；不要透露预期结论或怀疑的缺陷。后续轮次给同一审查模型此前的 finding ledger、状态和修复证据，以及新改动；不要加入新的预设结论。

发起后不要修改本轮审查范围内的文件，直到审查结果返回。可继续处理范围外工作，但不要让审查者看到与 brief 不同的差异。

要求审查者：

- 只读检查当前差异及相关调用方，找出实际 bug、意图不符或多余的行为改动。
- 不启动子代理，不修改文件或执行远端写入。
- 用稳定 ID 和证据报告发现。`blocker` 表示用户要求的场景不工作；`should` 表示范围内会触发的实际缺陷；`nit` 表示其余建议。只报告能指向代码、调用方或检查结果的问题。
- 按以下格式作答：

  ```text
  VERDICT: APPROVE 或 CHANGES
  R1 [blocker|should|nit] path:line 问题与影响。证据：... 建议：...
  ```

在 T3 Code 中每轮使用一次 `delegate_task`，`role: "review"`、`mode: "async"`，并保存 task ID。新一轮新建委派并带上当前 diff 与短 ledger。遵循 T3 的事件唤醒机制，不轮询或用 sleep 等待。超时、错误、无回复都不是通过；按平台要求取消失败任务后再决定是否重试。

## 处理发现

对每项自行复核，不因审查者给出的严重等级或 APPROVE 改变证据标准。

- 目标是解除有效 finding，不是无条件让审查者满意。确认的 blocker / should 只做能修复该根因的最小局部补丁；避免借机重构、增加通用层/配置/兼容分支或清理无关代码。当用户意图需要回归保护时，添加一个针对该缺陷的测试。
- 不同意 finding、认为证据不足或建议超出原范围时，直接说明理由，并用源码、调用方、可复现结果或检查输出来支持；记录为 `declined`，可列为后续建议。证据支持的 `declined` 会关闭该 finding；只有新的相关证据才重新打开，重复原意见本身不算新证据。不要为了避免反驳而照单全收。
- nit 只有在修复很小且不扩大范围时才处理；否则记录为 `declined` 或后续项。评论、文档、格式修改不值得开启新一轮。
- 每轮维护 ledger：稳定 ID、严重级别、状态（`open` / `fixed` / `declined`）、证据和修复路径。修改后运行受影响检查并记录结果。

## 收敛与交付

只有同时满足以下条件才报告 `APPROVED`：当前行为差异已由审查者覆盖、没有开放的 blocker / should、所有剩余 nit 已有证据支持的处置，且主 Agent 自查没有未解决的风险。

仅当行为代码变化、仍有 blocker / should，或审查结论没有覆盖当前行为差异时，且预算尚有余量，才开下一轮。预算用完、审查者失联、仍为 `open` 的同一发现经过两轮证据交换仍无法收敛，或关键检查无法运行时，报告 `NOT APPROVED` 或 `BLOCKED`，列出双方证据和下一步。评审者重复反对一个已有证据支持的 `declined` 项，不单独阻止收敛。不要把模型同意当作合并授权或 PR 写入授权。

最终汇报轮数、审查模型（如实际返回）、diff 大小变化、修复项与拒绝项、检查结果、usage / 费用是否可见，以及是否发生任何远端写入。此技能本身不授权创建 PR、推送、评论、合并或其他外部写入。
